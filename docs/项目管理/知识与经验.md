# CapsWriter-Offline｜开发知识与经验手册

> 目标：把从产品规划到 Windows 桌面发布的过程沉淀成未来可复用的个人知识库。本文件持续追加，且必须区分“原理”“经验建议”“本项目实践与证据”。不要将未实施方案写成已经完成的教程。

## 一、真实项目的协作与产品经验

### 01｜需求、方案、任务、验收是四回事

- **需求（Why）**：用户要“下载后能直接使用、自己找到合适语音模型”，而不是“必须新增某个类”。
- **方案（What/How）**：如首次安装向导、模型清单、下载器和硬件推荐。
- **任务（Scope）**：如 M1-A 只实现路径与状态接口，禁止顺手重写 GUI。
- **验收（Evidence）**：用实际下载、模型加载、真实听写、失败恢复验证，不以代码提交代替验收。
- **经验**：每个任务写清业务价值、受影响文件、风险、保护边界、退出条件和未包含内容，避免不断扩大范围。

### 02｜前端与后端的分工

- **产品/UI 层**：解释模型差别、展示状态与错误、实现流程与用户控制；不自行复制下载校验算法。
- **业务服务层**：模型清单、任务队列、重试、校验、安装和切换；独立于 NiceGUI 页面生命周期。
- **系统适配层**：系统路径、Windows 快捷键、麦克风、权限、GPU 和进程管理。
- **经验**：真正的前后端协作首先要谈接口契约、状态定义和错误码，而不是先画完页面或先写完服务。

### 03｜设计决策记录（ADR）的简化做法

每个重要决定简要保留：**背景 → 可选方案 → 选用方案 → 放弃原因 → 风险 → 何时重评**。如“Windows 首发而非一次支持三系统”，是降低驱动、全局按键、输入权限和打包验证成本，不代表未来不支持其他系统。

## 二、桌面技术学习笔记

### 01｜PyInstaller vs Inno Setup

- **PyInstaller**：将 Python 解释器、代码、依赖与资源收集为 Windows 可运行的文件目录（onedir）或单一 EXE（onefile）；它不是通用安装器，不应混淆“可执行文件”和“安装向导”。
- **Inno Setup**：把已构建且验证可运行的软件制作成用户可安装的 Setup.exe，处理文件复制、桌面/开始菜单快捷方式、卸载和升级动作。
- **GitHub Releases**：承载已审核发布产物、版本说明和校验文件，和源码分支、PR 有不同职责。
- **建议链路**：Python 源码 → PyInstaller onedir → 在干净 Windows 环境验证 → Inno Setup 安装版；同时按同一可复现构建产物生成 Portable ZIP。
- **实践状态**：项目当前有 PyInstaller/ZIP 发布脚本；正式安装器尚未落地。实际参数须以用户批准的构建脚本与测试报告为准。
- **相关网址**：[PyInstaller 文档](https://pyinstaller.org/) · [Inno Setup](https://jrsoftware.org/isinfo.php) · [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)

### 02｜安装版与免安装版

- Setup.exe 是 **安装器**；启动用的 App.exe 是 **软件本体**；二者都以 .exe 结尾。
- ZIP 便携版通常解压即用，可能也保存少量数据到系统目录，并不保证完全无痕。
- 安装版把**可替换程序文件**与**长期保留用户数据**分开，方便覆盖升级和卸载；便携版通常延续相对目录。
- 设计安装版时必须考虑非管理员、目录权限、中文路径、退出流程、数据迁移、快捷方式、签名与许可证。

### 03｜为什么模型安装需要清单与事务

- 模型“文件存在”不等于“文件完整”，更不等于“模型已经载入内存可以识别”。
- 清单需记录模型 ID、量化变体、文件路径、版本、大小、SHA-256、来源、许可证与后端兼容性。
- 正确安装：下载至隔离暂存 → 验证下载文件 → 安全解压并检查路径与空间 → 检查必需资源 → 验证可加载 → 安装并更新状态；失败不得覆盖可用旧模型。
- 网络断点续传必须核对 Range/ETag 或同等版本证据；不可无条件拼接旧内容。
- 推理后端：ONNX Runtime (CPU/DirectML/CUDA 等) 和 GGUF llama.cpp (CPU/Vulkan 等) 与 GPU 驱动、平台的能力不同；推荐算法需要实际检测与可解释的回退。
- **实践状态**：上面是需求与工程设计原则，M1-C 完成前不得写“自动下载已实现”。

### 04｜路径解析为什么要无副作用

- **问题**：源代码、便携 ZIP、未来安装版有不同的资源目录与用户数据目录。
- **原则**：读取路径（resolve）只计算路径，**不顺手创建目录或移动用户文件**；真正需要写文件时再由明确的写入动作检查权限并创建。
- **设计经验**：优先建立统一路径契约，并用隔离临时目录测试中文路径、旧便携布局、权限限制；让配置、GUI、模型检测共用该接口。
- **本项目实践进度**：Codex 的 M1-A 报告声称新 `paths.py` 已保留旧便携路径且解析无副作用，测试 30/30。**网页端尚未取得该本地提交源码，不能把实现细节当作独立复核结论**。见 [M1-A 回执摘要](回执/M1-A-本地实施摘要.md)。

### 05｜模型文件状态与运行就绪状态分离

- **文件状态**：未安装、部分安装、待验证、已验证、损坏等，回答“磁盘上的文件可靠吗”。
- **运行状态**：未启动、加载中、就绪、加载失败等，回答“本次语音输入是否可用”。
- **工程教训**：端口开放只能说明服务监听，不能证明推理模型已加载；文件存在不能证明未损坏。
- **本项目实践进度**：据 M1-A 本地报告，已新增状态基础层；真正的端到端就绪信号与无模型 GUI 启动属于后续 M1-B，需要真实验证。
