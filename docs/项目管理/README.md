## 协作闭环

1. **网页端**：与用户讨论，区分【已确认决定】【待讨论建议】【已实施证据】。生成任务文件，注明 ID、基线 SHA、目标、范围、保护边界、验收、输出位置。
2. **用户**：确认任务，决定是否允许 Codex 修改代码、运行真实服务及上传。未确认时只读。
3. **本地 Codex**：先读根 AGENTS.md、本入口、当前交接与对应任务；核实真实本地 Git/文件；依范围实施并完成测试。不得因任务在 GitHub 上就推断可以提交或推送。
4. **交付**：按任务 ID 写回执，包含状态、差异、测试证据、不能验证的功能、本地现存改动、提交 SHA；在用户授权后由独立分支/PR 或指定方式推送。
5. **网页端**：阅读回执与变更，进行设计复核，将任务推进为“待用户验收”；仅得到实际验收证据后才标记“已验收”。
6. **用户**：最终验收。回执与路线图记录明确结果，不以 AI 的“已完成”代替实际验证。

工作状态固定为：**待讨论 / 已确认待实施 / 实施中 / 已交付待验收 / 已验收 / 暂停**。单一活跃任务，必要时另开独立任务分支，避免互相覆盖。

## Git 纪律

- 网页端提交文档建议使用独立 `docs/` 分支和 PR；**不直接合并 master**。本地回执使用 `task/` 分支或经用户许可的同一文档协作分支。切忌双方同时编辑同一个活跃文件。
- 同步文档应先 `git fetch`，再用 `git show origin/分支:路径` 只读查看；**不需要 checkout/reset/clean/pull** 就能获取任务内容。未明确授权不得推送、部署、业务重启。
- 将文档 PR 合并到 master 前，先确认原有本地未提交内容和可能发生的路径冲突。尤其注意现有 11 项改动（包含未跟踪 build.spec、开发指南、测试文件及已删除脚本）。
- 不将用户隐私、个人配置/API Key、模型权重、下载缓存、日志、历史、转写产物、备份或未知二进制文件上传。对候选源码、测试、脚本、依赖许可和密钥进行单独审核。
- 可能转换为私有库：先确认 GitHub 连接有私有仓库读取权限。将来面向公众的软件站、安装包、模型文件必须有可公开访问的分发位置，不能依赖私有仓库 Release。

## 任务/回执命名

- 任务：`任务/任务ID-简述.md`，如 [W01 本地盘点](任务/W01-本地上传候选盘点.md)。
- 回执：`回执/任务ID-执行回执.md`，若需修订则保留前版与日期/提交差异。
- 对新任务发布，先写完整任务文件，再更新 [当前交接](当前交接.md) 的指针；不得只口头声称“已同步”。
- 可将重大产品选择与理由录入路线图或任务正文；当前交接只引用，不复制整段。
